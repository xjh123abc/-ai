# 银行清算状态与 OCR 三层字段

## Problem

银行回单的清算字段目前以布尔候选呈现为“已清算”，无法清晰表达“未清算”和“无法确认”。单据审核页也把可编辑字段集中展示，而账号、流水等辅助信息与记账关键字段没有区分，原始 OCR 文字另有折叠入口但缺少明确的信息层级。

## Solution

银行回单清算状态提供“已清算”“未清算”“无法确认”三个中文选项，并在结构化数据中保留为三态值。只有已清算可以满足银行清算核对；未清算与无法确认均不能作为已清算证据。

单据审核按三层组织识别信息：

1. **记账关键字段**：按单据类型显示金额、日期、付款方、收款方、发票号码、税额、费用事由等适用字段。字段提取给出候选值时预填并标记待确认；无法得到明确候选值时留空，必须由人工核对后保存确认版本。
2. **业务辅助字段**：银行账号、开户银行、电子回单号、交易流水号等候选完整展示并保留供查重、匹配和追溯，默认折叠。账号显示完整值。辅助字段布局与关键字段保持一致。
3. **OCR 完整原文**：包括银行说明、表头、备注等，完整保留并按需展开查看，不转换成可编辑的会计字段。

## User stories

- 作为财务人员，我可以明确选择银行回单“已清算”“未清算”或“无法确认”，从而准确表达回单证据。
- 作为财务人员，我可以先核对预填的关键记账字段，并查看折叠且完整显示的业务辅助信息或完整 OCR 原文，从而按需完成确认。
- 作为核对与追溯流程，我可以读取完整辅助字段和 OCR 原文，同时降低账号在界面上的暴露。

## Decisions

- 银行清算状态是三态业务值，不再把缺失值兼作“无法确认”。API / 结构化字段以稳定枚举值表示，界面显示中文选项；现有 true / false / null 候选须兼容读取或归一化为对应三态。
- 只有“已清算”可使银行清算检查通过；“未清算”保持未清算异常，“无法确认”进入需复核状态。
- OCR 关键字段是候选，不是已确认事实。预填不等于确认；人工保存仍生成新的确认版本。
- 辅助字段和全文继续关联原始单据及提取版本。业务辅助字段显示完整识别值，并与关键字段采用一致的对齐布局。
- 层级按当前单据类型显示适用字段，不要求每类单据都有相同字段。
- 不新增低置信度自动确认规则；候选仍需要人工确认，歧义或没有明确候选的字段不自动填值。

## Testing decisions

- API seam：上传/读取银行回单抽取及字段确认接口，观察三态候选与保存值、辅助字段/完整原文保留、以及核对只接受“已清算”。不能证明 OCR 在所有真实票据上的识别准确率。
- Browser seam：银行回单审核流程，观察关键字段预填且待确认、辅助字段默认折叠且显示完整值、原文按需展开、三态可选择并可保存。不能代替不同票据版式的识别质量评估。
- 现有 prior art：API 字段候选与确认版本覆盖于 `tests/api/test_workflow_roles.py`；浏览器单据确认与银行回单流程覆盖于 `apps/web/e2e/purchase-workflow.spec.ts`。

## Out of scope

- 更换 OCR 提供方或模型、建立所有票据类型的准确率承诺。
- 将 OCR 全文自动转成可编辑字段或自动确认会计事实。
- 改造业务关联、凭证生成、ERP 写回和其他会计核对规则。
- 改变原始文件访问权限或对账号字段实行后台加密策略；本规格要求界面默认脱敏并保留数据供内部匹配追溯。
