# 账清 AI｜乱序票据归集与整组确认：增量 PRD V0.1

日期：2026-10-29　｜　性质：**基于已有 MVP 的增量需求，不是重做产品**

## 1. 一句话需求

财务人员收到的发票、入库单、银行回单、报销单和其他费用票据往往分散、乱序到达。系统允许每张单据独立上传，**AI 持续推荐哪些单据属于同一业务**；未凑齐时提示缺什么，凑齐后展示整组证据，用户**只确认一次整个业务组**，随后接入已有核对和凭证流程。

本次目标是减少人工翻找、分类和反复建组的时间，而不是新增 ERP 或财务管理模块。

## 2. 用户实际操作路径

```text
任意时间上传一张单据
  → 已有 OCR / 单张字段确认
  → 待归类池（保留原件，不强制立刻创建业务）
  → AI 重新查看当前账套尚未归类的已确认单据
  → 展示「疑似同一业务」候选组、依据、缺口
      ├─ 仍缺当前情境必需的证据：留在待归类池，继续等待
      ├─ 业务归属不明确：提示疑点，暂不显示可确认状态
      └─ 当前情境所需证据齐全：预览整组 → 一键确认整组
  → 已有业务核对 → 符合会计规则才允许生成凭证草稿
```

**两种确认不能混淆：**

- **OCR 字段确认**：沿用当前实现，可以逐张核对识别字段。
- **业务归属确认**：只能对系统汇总的整个候选组一次确认，不能要求用户逐张点击“归属本业务”。

## 3. 首期业务范围与“凑齐”的含义

| 场景 | 典型材料（不是固定张数） | 什么时候给出「可确认整组」 |
|---|---|---|
| 已收货且已付款的采购 | 发票、入库单、银行回单；可能还有合同、验收单 | 至少能相互印证采购、收货和付款；合同/验收单按已有事实决定是否需要 |
| 员工费用报销 | 报销单、餐饮/住宿发票、出租车票、通行费票据、付款或报销回单 | 能判断同一报销事项、费用内容及当前付款状态；一张或多张费用票据均可 |
| 公司直接支付的费用 | 费用票据及付款证据；可能没有报销单 | 能判断费用事项及对应支付，不强制出现报销单 |
| 尚未付款的费用 | 费用票据及能说明该事项的材料 | 可以归成独立业务候选，但不得因此虚称“已经付款”或自动生成银行付款分录 |

**“凑齐”不是必须有 3 张，也不是 AI 猜测以后绝不会出现新单据。** 根据已识别的业务类型、付款状态、关联字段判断当前情境所需证据；判断不出来就标「需核实」，不要强行凑一组。

归组完整与制证充分是两个门槛：某个费用事项可以确认归组，但若现有核对规则仍要求付款证明等证据，凭证仍保持 `NEEDS_REVIEW`。首期不改写复杂费用会计政策。

## 4. 前端只新增一个最小交互

在现有单据中心增加「待归类」视图和「AI 推荐业务组」卡片，无须重做导航。

每张候选组卡片只展示：

1. 业务类型/大致用途，以及本组所有单据的缩略信息和金额。
2. **为什么认为它们是一组**：企业/人员、订单或合同编号、金额、日期、商品/费用内容等可查证信息。
3. 当前还缺什么、有什么矛盾；对票据数量不设通用固定门槛。
4. 仅在归组条件满足时显示「确认整组」；点击后一次性写入本组所有单据关系。

确认前不创建正式 `BusinessEvent`；已归类、未归类、待字段确认的单据状态应能一眼区分。手动建组入口继续保留，便于纠正 AI 错误。

## 5. 功能验收

| 编号 | 必须看到的结果 |
|---|---|
| P1 | 单据单独上传后一直保留在待归类池，上传顺序不影响结果 |
| P2 | 先收到银行回单、几天后收到发票和入库单，采购业务自动出现整组推荐；缺必要单据时不能误显示「确认整组」 |
| P3 | 两笔金额相同但供应商不同的采购不能因为金额相同就被直接拼在一起；展示真实匹配依据和疑点 |
| P4 | 用户只点一次「确认整组」，本组全部关联关系一并保存，原有核对流程可接着执行 |
| P5 | 费用组可有 1、2、5 张或更多相关单据；根据事项及付款状态判断，而不是硬编码“三张” |
| P6 | 费用组可以完成归类但因缺少制证证据而保持待复核；不能绕过已有会计核对和审核规则 |
| P7 | 既有 45,200 元三单采购→核对→凭证草稿→审批/CSV 的回归流程继续通过 |

## 6. 实验数据与求职展示

先制作 **2 笔采购 + 1 笔费用报销** 的关联正确答案，使用虚构字段和标记“测试无效”的模拟票据；把它们打乱、延迟、缺失和混入同金额干扰单据。真实脱敏票据只承担 OCR 版式评测，不强求真实票据本身凑成完整业务。

分别测量：候选归组正确率、错误关联数、人工确认操作次数、从上传到整理完成的耗时。与“人工找单据、手动选择每张关联”的旧流程对比；**只记录实测结果，不预写漂亮指标**。

## 7. 明确不做

- 不做自动确认业务组、不逐张确认业务关联、不直接自动入账。
- 不做一对多金额分摊、多合同跨期结算、已入账业务的静默追加或覆盖。
- 不接入柠檬云付费 API、RPA、n8n、消息队列或新的 ERP 系统。
- 不重写现有 OCR、会计科目、凭证审批或前端页面架构。

此 PRD 只定义本次增量。旧 V2 仍是整体产品背景，遇到范围差异以本文件为准。
