# 账清 AI｜乱序票据归集：最小技术实现方案 V0.1

日期：2026-10-29　｜　目标：**最少接口、最少改动、保留已跑通 MVP**

配套需求：[`08_乱序票据归集_增量PRD.md`](08_乱序票据归集_增量PRD.md)。本文件是供 Codex 后续实施的设计，**不是已完成功能清单**。

## 1. 真实仓库基线：哪些不用重做

| 已存在 | 当前代码位置 | 此次如何使用 |
|---|---|---|
| 单张上传、OCR、字段人工确认 | `services/api/app/routers/workflow.py`：`POST /documents`、`PATCH /documents/{id}/extraction` | 原样复用；确认的是 OCR 字段，不是业务归属 |
| 单据及版本 | `DocumentAsset`、`DocumentExtraction` | 待归类单据直接使用现有记录，不新增任务表 |
| 业务及其证据关系 | `BusinessEvent`、`BusinessEventDocument` | 整组确认时一次写入，保留确认人、角色、提取版本 |
| 建组接口 | `POST /api/v1/business-events` | 优先复用一次提交多张文件的能力 |
| 核对与凭证 | `POST /business-events/{id}/reconcile`、`POST /business-events/{id}/voucher-drafts` | 确认整组后沿用；核对不通过不生成草稿 |
| 单据类型候选 | `packages/ingestion/candidates.py` | 已有出租车票、通行费、验收报告等类型线索；需补齐业务角色映射 |
| 前端工作台 | `apps/web/src/App.vue` | 仅在现有单据中心加待归类及候选组卡片 |

当前最直接的缺口：

- 现有 `/documents?work_queue=true` **不是**“尚未关联任何业务”的严格筛选，不能直接拿来当待归类池。
- `EventCreate` 目前最少要求 2 份文件，`EXPENSE` 创建时强制要求 `PAYMENT_PROOF`；会挡住合理的单据较少的费用候选。
- `role_type()` 目前只支持发票、入库单、银行回单、支付证明、合同；不能把出租车票/通行费/验收单等按本身类型关联进业务组。
- 尚无“读出一组推荐及理由”的接口和前端卡片。

## 2. 唯一新增链路

```text
已有上传 / OCR 字段确认
    ↓
待归类池：查 DocumentAsset 中尚未归属 BusinessEvent 的单据
    ↓
推荐：基于同账套已确认字段，提出完整候选组及缺口
    ↓
一屏预览全组：文件、角色、匹配理由、业务情境、缺失/矛盾
    ↓ （仅 group_ready=true）
用户一次「确认整组」
    ↓
复用 POST /business-events（一次传所有 document_ids + roles）
    ↓
已有 reconcile；符合原有财务条件时才走 voucher-drafts
```

**先不存储 AI 的未确认候选组。** 它们只是查询时算出的预览结果；文件在数据库里持续保留，几天后补传文件时重新计算推荐即可。只有用户确认整组才创建正式业务关系。不做后台监听、消息队列或候选组状态表。

## 3. 最小接口和数据契约

### 3.1 待归类池：扩展现有列表

`GET /api/v1/documents?unlinked_only=true`

- 在已有 `GET /documents` 增加可选参数：查询本账套**没有有效 `BusinessEventDocument` 关联**的文件；保留原有分页、权限和返回结构。
- 返回未确认 OCR、已确认但未归类和识别失败的文件；前端分别显示状态。**只有 `DocumentExtraction.status=CONFIRMED` 的文件可以进入正式推荐与建组。**
- 不替换原有 `work_queue` 的语义。

### 3.2 推荐整组：新增一个只读接口

`GET /api/v1/business-event-suggestions`

响应结构示例（ID、金额、理由均为示意）：

```json
{
  "groups": [
    {
      "event_type": "PURCHASE",
      "scenario": "PURCHASE_PAID_RECEIVED",
      "documents": [
        {"document_id": "doc-a", "role": "INVOICE"},
        {"document_id": "doc-b", "role": "GOODS_RECEIPT"},
        {"document_id": "doc-c", "role": "BANK_RECEIPT"}
      ],
      "reasons": ["发票销售方与银行收款方一致", "货物与入库信息相关"],
      "missing": [],
      "conflicts": [],
      "group_ready": true,
      "voucher_ready": false
    }
  ]
}
```

`group_ready` 仅表示**可以一次确认业务归属**；`voucher_ready` 不是模型推测的正式结果，首期统一为 `false` 或不返回，制证资格由已有 `reconcile` 实际决定。前端不得用它绕过核对。

推荐实现保持短路径：

1. 从本账套读取**已人工确认的**单据摘要（类型、购买/销售方、付款/收款方、金额、日期、单据号、合同号等），不依赖文件上传时间来判断所属业务。
2. 用最基本的字段关系形成可能的组合；金额相同不能单独成立，明显不同的交易方不能直接判同组，分批款不能被简单当成金额冲突。
3. 在 `packages/ai/` 使用**当前已配置的 DeepSeek 调用方式**，仅对这些结构化字段做一次候选组判断与理由生成；不新建通用 Agent 框架，不传完整原件。校验输出中的单据 ID 必须来自本账套本次候选池。
4. 在 `packages/reconciliation/` 用少量确定性业务条件产出 `group_ready / missing / conflicts`。模型负责**提出候选和解释**，不能宣称会计凭证已可生成。
5. 模型不可用时明确显示“本次推荐不可用”，原有手动建组继续可用；不要把规则候选冒称 AI 结果。

### 3.3 一键确认：复用现有建组接口

前端将**整组** `document_ids`、对应 `roles`、`event_type` 和简短原因一次提交给 `POST /api/v1/business-events`。确认按钮只出现一次，不对每张单据显示“确认业务归属”。

最少后端调整：

- 允许 `EventCreate` 为单据数较少的 `EXPENSE` 接受 1 张或更多已确认单据；**取消创建时必须带 `PAYMENT_PROOF` 的限制**。这只允许建组，不等于通过费用核对。
- 在 `role_type()`/确认字段类型约束中补充 `TAXI_RECEIPT`、`TOLL_RECEIPT`、`ACCEPTANCE_REPORT`，并支持人工选择/确认 `REIMBURSEMENT_FORM`（首期只补必要的日期、员工/用途、金额字段；不开发专用 OCR 模型）。餐饮/住宿发票沿用 `VAT_INVOICE` 类型。
- 沿用现有 `BusinessEventDocument` 一次性记录所有关联、证据版本、操作者和理由。一个未归类文件不得被 AI 直接写入多个正式业务组。
- 当前采购三单规则、其他既有业务类型和凭证核对逻辑不做宽松化修改。

## 4. “几张票据算齐”由场景决定

不要实现 `if number_of_documents >= 3` 这种规则。

| 情境 | 归组条件的最小判断 | 制证边界 |
|---|---|---|
| 采购、已收货已付款 | 发票/入库/已清算付款能被同一交易主体和业务信息串联 | 原有 `PURCHASE` 核对通过才制证 |
| 员工多票报销、已报销 | 一个报销事项下关联的费用票据、员工信息和实际报销/付款证据相符；有报销单则用于串联 | 原有 `EXPENSE` 核对不通过则保持 `NEEDS_REVIEW` |
| 公司直接支付一笔费用 | 有费用事项及相关付款事实；没有报销单也可能合理 | 不把付款申请当成银行已清算 |
| 员工尚未领到报销款 | 已能确认某个费用/报销事项，当前没有银行付款事实 | 可以归组，但不能据此生成银行付款凭证 |
| 一张独立费用票据 | 仅在字段能充分说明独立费用事项时才给单张组建议；否则待补充 | 不能仅凭“有一张票”跳过已有制证证据要求 |

不能判断当前情境时，返回 `group_ready=false` 和明确缺失或疑点，等待补充/修正已识别字段。费用票据多少张由同一报销事项的事实关联决定，而非一个强制数量。

## 5. 最小开发任务：一次交给 Codex 一个

### T01｜待归类池与整组就绪判断

- 扩展 `/documents` 查询，展示未归类状态；`packages/reconciliation/` 实现小函数，根据已确认字段返回候选组、缺口和 `group_ready`。
- 验收：采购回单先到，单据保留但不会立刻建业务；随后发票和入库单到齐，返回三张一组；费用组不按固定 3 张判断。
- 本任务**不碰凭证生成、ERP、模型提示词和审批**。

### T02｜AI 推荐与整组预览

- 新增只读推荐接口，接入当前 DeepSeek 模型；现有 `App.vue` 加一张整组候选卡片（理由、缺失、全部文件）。
- 验收：金额相同但交易方不同的干扰票据不会被当作确定关联；不齐全时没有「确认整组」按钮。
- 不增加新页面框架、后台任务、向量库或自动关联。

### T03｜一次确认及回归

- 复用 `/business-events` 一次提交完整组；补齐少量费用单据角色与 1 张费用建组能力，随后调用已有 reconcile。
- 验收：一次点击完成整组关系入库；费用可归组但缺会计证据仍不能制证；45,200 元现有采购全链路测试不退化。
- 自动化测试以少量**结构化合成样本**覆盖乱序、缺失、同金额干扰、费用 1/2/5 张和整组一次确认，另用少量真实脱敏票据单独验证 OCR。不要为了测试去寻找 20 套真实完整票据。

## 6. 不增加的设计

不新建数据库表、持久化候选队列、定时轮询、消息总线、微服务、模型训练系统、自动入账、ERP 接口或复杂多对多付款分摊。现有流程与权限、审计、原始证据、金额校验属于已具备的正确性边界，**复用而非重新开发一遍**。
