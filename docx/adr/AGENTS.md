# 账清 AI｜项目级 AGENTS.md

## 目标与当前任务

- 本项目是个人求职作品：把中国财务单据从上传、OCR、业务关联、核对到凭证草稿的链路做扎实，不以商业化平台为目标。
- 当前增量任务是**乱序单据归集与整组确认**。先读 `docx/08_乱序票据归集_增量PRD.md` 和 `docx/09_乱序票据归集_增量技术方案.md`；旧 V2 文档是整体背景，不得据此扩大本次任务。
- 用户只要求规划或文档时，**不得修改业务代码、提交 GitHub、创建 PR**。要实施代码，必须收到明确指令。

## 固定架构

- `apps/web/`：Vue 3 / TypeScript / Vite，负责单据池、候选业务组、整组确认和现有凭证页面。
- `services/api/`：FastAPI / Pydantic / SQLAlchemy，负责接口、账套权限、单据及业务持久化、事务和审计。
- `packages/ingestion/`：OCR、文件解析、单据类型和字段候选。
- `packages/reconciliation/`：候选业务归组、证据是否齐全、确定性核对。
- `packages/ai/`：DeepSeek 结构化建议及解释；AI 不能直接确认业务或生成正式记账事实。
- `packages/connectors/`、`packages/posting/`、`packages/vouchers/`：沿用现有导出、审批和凭证实现，本次不重构。
- PostgreSQL 保存已有 `DocumentAsset`、`DocumentExtraction`、`BusinessEvent`、`BusinessEventDocument` 和凭证/审计数据；优先复用，不新建平行数据模型。

## 开发方式

1. 先检查 `git status`、真实代码和已有测试，再动手；保留用户的改动。
2. **一次只完成技术方案中的一个小任务**，先跑通再进入下一个；不顺手改无关功能。
3. 不引入微服务、消息队列、工作流平台、复杂 Agent 框架或通用规则引擎；现有单体和一次请求内处理足够。
4. 遇到业务规则、交互或核心架构的歧义，**先问用户**；修改固定架构前先说明原因并取得确认。
5. 票据独立上传；AI 可以提出整组候选，**只由用户一次确认整个业务组**，不能逐张要求确认业务归属。原有逐张 OCR 字段确认保持不变。
6. 费用单据数量不固定；业务归组确认不等于会计凭证可生成。原有核对、权限、金额、证据版本和审批约束不得绕过。
7. 不接入收费 ERP API、不实现 RPA、自动付款、自动过账或生产入账；没有实际验证的能力不写成“已实现”。
8. 每个任务仅补必要的 API/单元测试和一条端到端回归；完成时报告改了什么、实际测了什么、尚未完成什么。
