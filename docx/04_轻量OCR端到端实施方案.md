## 1. 目标和完成定义

本方案把现有产品要求转成可按序执行的工程任务。先完成一条本地纵向链路，再在该链路上补齐 PRD 的 P0 最小 MVP。第一阶段只证明从原始单据到待人工入账导出可以完整流转；它不等于具备生产身份权限、租户隔离或正式 ERP 写入能力。

### 第一条纵向链路

使用「采购入库付款」样例中的发票、入库单、银行回单：

```text
JPG/PNG 上传与原件留存
  → 本地 CPU OCR 和带 bbox 的字段候选
  → 人工确认字段及三份证据的业务关系
  → 金额、主体、入库和银行清算确定性核对
  → 按明确的测试会计政策生成凭证草稿
  → Decimal 借贷、期间、科目和重复检查
  → 制单人与审批人分开操作
  → 通用凭证文件导出，状态为 EXPORTED_PENDING_MANUAL_POST
```

只有上述链路正确并可由 API 与前端复现，才开始扩展其他 MVP 案例。没有经授权并验证的 ERP 连接时，任何页面和 API 均不得显示 `POSTED` 或 `VERIFIED`。

## 3. OCR 选择与本机实测

### 3.1 初始实现配置

- Python 包：`rapidocr==3.10.0`；CPU 推理引擎：`onnxruntime==1.31.0`。
- 检测与识别：PP-OCRv6 Tiny，中文路线；不启用方向分类器。最初使用 `intra_op=4`、`inter_op=1`；端到端资源测量超过门槛后调整为 `2/1`，并将 OCR 输入长边限制为 1,800 像素。原件不变，缩放后的 bbox 按宽高比例映射回原图坐标。方向异常须显示待处理状态，不能无提示地漏识别。
- 模型文件由 RapidOCR 官方模型仓库校验下载；本次 Tiny 检测和识别模型约 1.74 MiB 与 4.28 MiB。正式部署通过配置指定模型缓存目录，不把模型或票据写入 Git。
- `ExtractionProvider` 隔离识别引擎；模型只生成候选值，不做业务事实裁定、会计判断或 ERP 写入。

RapidOCR 官方将 PP-OCRv6 Tiny 列为轻量路线并包含中文支持；官方已说明旧 `rapidocr_onnxruntime` 包逐步退役，因此新实现不使用旧包。[安装说明](https://rapidai.github.io/RapidOCRDocs/main/install_usage/rapidocr/install/) · [模型列表](https://rapidai.github.io/RapidOCRDocs/main/model_list/)

### 3.2 本机基准结果

在 WSL2、Ryzen 7 5800H 可见 16 个逻辑 CPU 上，用上述 Tiny 配置顺序识别项目 15 张 JPG：

- 文件名标示金额的 10 张图片中，10 张均在 OCR 文本中找到对应金额字符串；这只是快速抽查，不代表所有字段准确率。
- 45,200 元采购三张图片中，发票号、日期、未税金额 40,000.00、税额 5,200.00、价税合计 45,200.00 均被识别；入库单与回单也识别到 45,200.00，发票购买/销售方与回单付款/收款方名称能在识别文本中找到。
- 15 张顺序处理平均约 2.84 秒/张，观测 p95 约 7.51 秒；进程峰值 RSS 约 346.7 MiB。图片尺寸、系统并发和冷启动会改变结果。
- 初始默认线程配置曾达到约 7 秒/张；限制为 4 个推理线程后，三张采购票据约 1.48–3.27 秒/张，进程峰值 RSS 约 215.6 MiB。

**结论：**这台机器可以作为单 worker、单张串行的轻量 OCR 开发机；当前结果足以开始纵向链路，不足以取消人工复核或推断生产准确率。生产前需建立人工标注答案集，分别统计单据分类、字段准确率、关联准确率及端到端耗时。暂不启用批量并发或 GPU。

2026-10-27 在同一台 Ryzen 7 5800H / 16 逻辑 CPU 开发机补跑了 15 张样例的顺序基准。当前配置下，模型加载 0.012 秒，单张 OCR 平均 0.435 秒、p50 0.361 秒、nearest-rank p95 1.232 秒，进程峰值 RSS 379.7 MiB。另将同样 15 张原图逐一经登录后的真实上传 API 测量，包含 multipart 处理、本地原件保存、OCR/候选提取和 SQLite 写入：平均 0.460 秒、p50 0.390 秒、nearest-rank p95 1.289 秒；首次请求 0.503 秒，warm p50 0.336 秒。API 进程 ru_maxrss 峰值 472.7 MiB、5 毫秒采样峰值 449.8 MiB，低于 512 MiB 开发门槛。口径不含网络传输和 PostgreSQL，不是生产容量压测；第一次 API 测量在 4/1 线程下曾达到 520.1 MiB，故按资源门槛调整到 2/1 后再测。报告分别见 `tests/fixtures/reports/ocr-benchmark-2026-10-27.json` 和 `tests/fixtures/reports/document-api-benchmark-2026-10-27.json`。候选数和置信度分桶**不是字段准确率**；长边超过 1,800 像素的三个样例被缩放，但它们没有人工金标，候选仍须人工确认。45,200 元金标图字段及其 bbox 回归测试通过。可分别重跑 `PYTHONPATH=services/api:packages services/api/.venv/bin/python scripts/benchmark_ocr_samples.py` 和 `services/api/.venv/bin/python scripts/benchmark_document_api.py`。全量人工金标准确率及 PostgreSQL/网络端到端压测仍未完成。

## 4. 目标模块、数据和接口

继续采用模块化单体，不新增微服务。计划把现有空目录按职责实现：

- `packages/ingestion`：文件类型校验、哈希、OCR adapter、文本/PDF/表格解析、字段候选与证据位置。
- `packages/evidence`：不可变原件、租户访问控制和页/框证据引用。
- `packages/domain`：Document、BusinessEvent、金额与状态模型。
- `packages/reconciliation`：候选关系、人工确认、可重放核对规则和差异。
- `packages/cases`：缺证、冲突、重复、金额或主体异常。
- `packages/vouchers`：会计政策输入、凭证版本、Decimal 重算和校验。
- `packages/ai`：`AccountingSuggestionProvider` 接口及结构化候选验证；本地规则建议与外部模型建议明确区分。
- `packages/posting` 与 `packages/connectors`：授权检查、导出 adapter 和后续 ERP adapter。新增 `vouchers`/`posting` 的接口和数据归属先写简短 ADR。
- `packages/audit`：追加式业务操作记录。
- `services/api`：身份、RBAC、事务、租户过滤和可审计编排；`apps/web` 只调用内部 API。

API/存储契约沿用技术方案中的实体并统一使用：

- Document：`id, tenant_id, account_set_id, sha256, mime_type, object_key, origin, uploaded_by, uploaded_at, processing_status`。
- Extraction：`document_id, version, document_type, field_key, raw_value, normalized_value, confidence, page, bbox, evidence_text, provider, model_version, status`。
- BusinessEvent 与关联表：保存角色、候选/已确认关系、理由、证据、金额分配、规则版本和核对状态。
- VoucherDraft 与 lines：版本、期间、日期、状态、政策版本、来源 hash；金额用数据库 `NUMERIC`，JSON 金额用十进制字符串。
- Approval、PostingAttempt、AuditEvent：保存不可变版本、决策、幂等键、请求摘要、回执摘要和操作者；不保存第三方 token。

内部端点按技术方案逐步提供：

```text
POST   /api/v1/documents
GET    /api/v1/documents
GET    /api/v1/documents/{id}
GET    /api/v1/documents/{id}/content
PATCH  /api/v1/documents/{id}/extraction
POST   /api/v1/document-batches/{id}/process
GET    /api/v1/business-events
GET    /api/v1/business-events/{id}
POST   /api/v1/business-events/{id}/reconcile
POST   /api/v1/business-events/{id}/voucher-drafts
GET    /api/v1/voucher-drafts/{id}
POST   /api/v1/voucher-drafts/{id}/validate
POST   /api/v1/voucher-drafts/{id}/submit-review
POST   /api/v1/voucher-drafts/{id}/approve
POST   /api/v1/voucher-drafts/{id}/export
POST   /api/v1/voucher-drafts/{id}/post                 # 仅授权后启用
GET    /api/v1/voucher-drafts/{id}/posting-status
GET    /api/v1/insights/summary                         # 当前权限范围内的业务处理指标；未接入总账时不生成财务指标
```

单据、业务、异常、凭证列表支持 `page` 和 `page_size`（服务端限制最大 100）；分页响应包含 `items/page/page_size/total`，单据和异常附带当前授权范围的工作台统计。所有 ID 都按当前用户 tenant/account_set 授权过滤。人工修正带 `expected_version`，版本冲突返回 409。API 返回 403/409/422/503 的业务错误，不由前端自行推进最终状态。

## 6. 核心状态与异常处理

### 6.1 单据与字段

- 单据处理：`UPLOADED → PROCESSING → EXTRACTED → NEEDS_REVIEW/CONFIRMED`，解析失败保留原件并记录 `FAILED` 和原因。
- 字段版本：自动候选、人工确认和后续纠正均保留版本；下游业务/凭证绑定具体 extraction version。
- 文件 SHA 重复时返回已有原件及重复提示，不重复生成新的账务候选；重复发票查重另按发票号+租户/账套/期间执行。

### 6.2 业务核对

- `MATCHED`：必要证据齐全且规则通过；`PARTIAL`：有部分证据或付款未清算；`NEEDS_REVIEW`：字段/主体/金额冲突，或业务已关联但关键证据缺失（例如缺银行回单）；`INSUFFICIENT_EVIDENCE`：现有证据不足以确认单据是否属于同一笔业务。
- 付款申请/支付证明只证明审批或付款意图；银行回单/流水才可作为银行清算证据。
- 缺收货、税额差异、票款差异、主体不符、重复或低置信度均生成带证据和规则版本的 case；禁止自动批准。

### 6.3 凭证与入账

```text
DRAFT → VALIDATED → PENDING_APPROVAL → APPROVED
     → SUBMITTING → POSTED_PENDING_VERIFY → VERIFIED
分支：NEEDS_REVIEW / REJECTED / FAILED / UNKNOWN /
      EXPORTED_PENDING_MANUAL_POST
```

- 草稿变更产生新版本并重新校验、审批；审批人不可批准自己创建的草稿。
- 写回前查幂等键和重复风险；超时先回查。响应丢失/无法确认写入结果进入 `UNKNOWN`，不自动重发。
- 导出不改变 ERP 真值；状态为 `EXPORTED_PENDING_MANUAL_POST`。具体导入格式未对照目标 ERP 官方文档前，不称为“柠檬云可直接导入”。

## 7. 测试矩阵和验收门槛

### 7.1 自动化与人工金标

1. 对 15 张原始图建立独立、人工复核的期望值文件；不修改原始样例目录。
2. OCR 指标分别记录类型分类准确率、关键字段 exact match、置信度分桶、单张耗时、峰值 RSS；不能只报一个平均“AI 准确率”。
3. API 测试覆盖文件魔数/MIME/大小/重复哈希、租户过滤、字段 `expected_version` 冲突、业务重放、Decimal 规则和状态迁移。
4. Playwright 覆盖上传 → 人工确认 → 业务关联 → 核对 → 凭证预览/修正 → 审核 → 导出或授权测试写回 → 回显结果。

### 7.2 必验场景

- 45,200 元发票、入库单、银行回单：金额/主体匹配，税额 5,200，分录借贷均为 45,200。
- 4,448 元多票费用：发票、回单、支付证明角色不混淆；税项与费用科目经政策确认。
- 904,000 元合同与两页验收：两页均可追溯，未验收完全时不允许通过。
- 6,780 元设备发票/回单、21,800 元租赁发票及独立出租车/通行费样例：不因金额或批次近似误合并。
- 缺回单、少入库、票款不一致、OCR 金额空缺、低置信度、重复上传、同票重复草稿：进入正确复核/拦截状态。
- 会计期间锁定、科目无效、借贷不平、辅助核算缺失：不能提交审核/批准/写回。
- 企业隔离、低权限用户审批/写入、审批自审、版本冲突、并发重复点击均被拒绝并留审计。
- Mock connector 写入 + 回读逐行一致才能 VERIFIED；超时为 UNKNOWN；无授权分支只能导出待人工入账。

### 7.3 本机资源门槛

- 首条链路 OCR worker 限制为一个并发任务；单张图片最大尺寸/文件大小由上传配置控制。
- 开发验收以 15 张样例顺序完成、OCR worker 峰值 RSS 不超过 512 MiB、错误文件不导致进程退出为资源目标；端到端耗时记录 p50/p95。若实测超标，先缩小输入图像边长和线程数，再评估换模型；不以交换分区代替内存预算。
- API、PostgreSQL 与 OCR 同时运行时重新测量 WSL 可用内存；生产并发容量需独立压测，不能从单机样例推算。

## 8. 明确不做与外部阻塞

- 不自建总账，不转账，不自动报税，不由 AI 决定费用/库存/固定资产科目，不对不完整证据补编事实。
- 本轮 MVP 不包含预测分析、复杂多实体合并或自由财务问答；FR-V2-12 作为 P1。
- 柠檬云授权、账套凭据、目标导入格式及测试环境均未在仓库验证。取得正式授权前，写回接口只定义并保持禁用；不可探测或声称联调完成。
- 当前原始数据不含完整人工答案；关键字段 gold set 必须由财务负责人/样例负责人确认，不能以 OCR 自己的结果作为正确答案。
- 用户已选择“本地规则先跑通，外部 AI 暂禁用”。外部 AI 建议仅在 provider、凭据和敏感字段授权落实后启用；在此之前产品只能标为规则候选，FR-V2-06 留为明确的 P0 阻塞项。
- PDF 目前由 PyMuPDF 解析。其官方文档说明该软件采用 GNU AGPL 或商业许可；生产部署/分发前必须确认 AGPL 义务适用性或取得商业许可，否则应替换为完成许可证审查的解析器。参见[官方许可证说明](https://pymupdf.readthedocs.io/en/latest/about.html)。
