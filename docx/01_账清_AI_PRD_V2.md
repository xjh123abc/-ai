# 账清 AI｜产品需求文档 PRD V2.0

更新时间：2026-10-26 · 状态：已按产品负责人新方向对齐，接口授权、会计政策及实际试点客户待验证

## 0. 一句话产品定义

**账清 AI 是中国中小企业的 AI 财务运营工作台。**连接发票、合同、入库单、验收报告、付款证明、银行回单以及 ERP 数据，通过 AI 理解与关联一笔业务，以规则核算与审批为防线，自动形成凭证并受控写入现有财务 ERP；随后进行对账、财务查询和经营风险分析。**现有 ERP 是正式账本，账清 AI 是上层智能操作与业务证据平台。**

参考 Mercury 的经营与资金信息工作台视角，以及 Truewind 的 AI 会计自动化方向，但产品、币种、票据格式、会计规则与集成路径均以中国企业为前提。

## 1. 必须解决的用户问题

1. 单据散落在微信、邮箱、共享盘、ERP、银行文件中；财务人员人工分类和拼接业务证据。
2. 明明使用了 ERP，仍需手工读发票、查合同/收货、录凭证、反复核对银行收支。
3. 缺票、未验收、重复付款、跨期、票款不符很容易在人工流程中漏掉。
4. 老板和财务负责人看得到报表，却难以追溯某个数字对应哪些原始交易，更不容易发现潜在现金流风险。

核心价值从「只是找异常」升级为 **业务财务流程自动完成 + 证据可追溯 + 财务运营可视化**。

## 2. 用户与权限

| 角色 | 第一版主要任务 |
|---|---|
| 会计/出纳 | 批量上传原始单据、补资料、确认字段、审核 AI 凭证草稿、查看写账进度 |
| 财务负责人 | 配置会计规则、审批凭证、查看异常、资金/费用/应收应付概览 |
| 采购/仓管/业务人员 | 在指定业务范围内补上传入库、合同、验收和付款申请，不默认看到全部财务数据 |
| 企业经营者 | 查看可解释的利润、资金、成本和风险指标；追溯凭证和业务证据 |
| 管理员 | 绑定企业账套/用户角色、配置授权、数据保留、模型使用政策和审计 |

## 3. 产品端到端业务闭环

1. **收集证据**：上传或授权读取 JPG/PNG/PDF/OFD 图片/票据、电子发票文件、结构化 Excel/CSV、ERP 财务/业务数据；区分外部已验证接入、用户文件和演示文件。
2. **抽取信息**：判断单据类型，从图像/文本提取企业名称、纳税人信息、日期、票号、商品行、金额、税额、付款方/收款方、银行流水号、合同号、验收/入库数量和证据定位；识别失败标“待确认”，不得填造事实。
3. **理解一笔业务**：将一张或多张发票、合同、入库、验收、银行回单分组，支持一对多、多对多、预付、分批入库、分期付款。人工可拆分/合并，但须保留审计。
4. **确定性核对**：按币种、主体、合同、收货、税率/税额和清算状态校验。不能仅凭金额相同自动认定同一交易；发现冲突进入异常分支。
5. **AI 制凭证**：基于证据、用户账套最新科目、企业会计政策及业务用途形成凭证候选；给出借贷科目、金额、摘要、辅助核算和理由/来源，不把概率性建议当成正式账。
6. **规则校验和审批**：校验借贷相等、有效科目、会计期间、进项税政策、银行/应付处理、重复凭证、差额和证据充分性。按角色确认后锁定草稿版本。
7. **正式入账/导出**：在用户已授权且测试联调通过的环境中由受控服务调用 ERP 官方写入能力，取得结果并回查正式凭证；若无权限，导出可导入的凭证文件，状态必须如实保持“待人工入账”，不可显示“已入账”。
8. **持续管理**：更新处理状态，关联银行与正式凭证对账；以实时可用且获授权的数据生成资金、费用、应收应付、异常和入账效率指标；每个数字能回到具体证据。

**关键原则：自动化的是信息处理和重复操作；企业保留授权、审批、例外处理与最终会计责任。**首个生产试点建议人工审批；未来经验证后可按企业显式策略对低风险类型开启受控自动审批。

## 4. P0/P1/P2 范围（替换旧版版本优先级）

### P0：真正可闭环的 MVP

- 企业、用户、角色、账套和授权状态。
- 单据上传/存储/预览/分类、文本与图片识别、字段来源定位、人工修正及版本记录。
- 同笔业务单据关联和确定性核对；多张发票、分批收货/付款、无票/无回单分支。
- 凭证草稿生成、审核前预览、借贷/期间/科目/税额校验与人工审批。
- ERP 写入适配器、明确的授权检查、幂等和回读核验；缺少第三方实际权限时提供导出兜底，但必须标注未完成真实入账。
- 异常工单、日志、关键处理 KPI、基础金额溯源问答。

### P1：试点后完善

- 定期同步/增量更新、发票查验接入、多票报销优化、冲红/退款/暂估、应收应付到期提醒、月末对账清单、报销审批与费用归集、跨部门协作。
- 老板和财务负责人可用的财务问答、费用趋势、资金收支、付款计划视图（基于数据权限和覆盖率）。

### P2：市场验证后

- 复杂多实体合并、现金流预测、预算与情景分析、多 ERP、大规模模型训练或复杂 Agent 协作。

### 非目标

自研总账、替换 ERP 原有会计凭证/报表系统；发起银行付款；自动报税/结账；自动修改历史正式凭证；没有验证权限却声称已连接银行/ERP。

## 5. 贯穿案例：45,200 元采购

输入三个真实格式的教学模拟文件：100 副 VR 眼镜发票（不含税 40,000 元、税额 5,200 元）、入库单（含税 45,200 元）和农业银行电子回单（支付 45,200 元）。

用户上传后应看到：

1. 三张单据均有文件状态、缩略图、类型、提取字段和可信来源。
2. 业务组展示：供应商、数量、应付/实付、税额、证据链接、单据匹配理由。
3. 完整且一致时可以提出凭证候选；例如该企业为一般纳税人且货物用于销售、进项可抵扣、同一会计期间已付款，候选为借库存商品 40,000、借应交税费—应交增值税（进项税额）5,200、贷银行存款 45,200。
4. 如果货物是自用设备、税额不可抵扣、只有预付款或跨期，应根据企业政策和证据调整科目/时点，不能照抄示例分录。
5. 审核人打开票据证据，确认并提交；系统执行授权的 ERP 写入并回读正式凭证号或明确告诉用户“ERP 未授权，仅已导出待入账”。
6. 对账详情和财务问答能从这笔交易回溯三个文件和正式凭证。

**第二条异常回归场景**：旧版订单 100 件、入库 90 件、全额发票/付款；必须进入“待补合同或收货证据/待复核”，不能强行过账或把未收 10 件定义为损失。

**第三条批量场景**：同一批上传含多张彼此不相关的发票，系统应分别创建候选业务，不得因为批次相同自动合并。

## 6. 前端信息架构与关键界面

| 页面 | 核心交付 |
|---|---|
| 财务工作台 `/workspace` | 本期待处理单据、待生成/待审凭证、写账失败、未匹配流水、基本收支/风险指标；主按钮“上传单据开始处理” |
| 单据中心 `/documents` | 拖拽/批量上传、OCR 状态、图片/文本预览、字段证据高亮、错误修正、补充资料 |
| 业务中心 `/business-events` | 按业务展示合同/发票/入库/验收/回单/付款关联和匹配程度；确认/拆分/合并 |
| 凭证中心 `/voucher-drafts` | 草稿借贷分录、会计科目、来源、规则校验、审批、执行记录、最终 ERP 凭证号或导出状态 |
| 核对与异常 `/cases` | 缺票、重复、收货/付款差异、税额问题、写回不确定等工单和处理轨迹 |
| 财务分析 `/insights` | 资金/费用/往来/利润等实际可得口径，来源覆盖和更新时间、证据溯源、问答 |
| 数据连接与设置 `/integrations` | 柠檬云账号/账套、权限状态、只读/写入能力、文件导入、同步时间、授权管理 |

兼容旧页面路由时可做导航重命名/跳转，不能破坏已存在的后端工单 API 或审计链。

## 8. 凭证状态（独立于异常工单）

`DRAFT → VALIDATED → PENDING_APPROVAL → APPROVED → SUBMITTING → POSTED_PENDING_VERIFY → VERIFIED`

异常分支：`NEEDS_REVIEW`（证据/会计政策不足）、`REJECTED`（审批拒绝）、`FAILED`（确认未写入）、`UNKNOWN`（接口超时/结果不明）、`EXPORTED_PENDING_MANUAL_POST`（仅导出）。

不得由前端直接改写最终状态；草稿一旦获审批，内容变更产生新版本并重新审批；未知状态不得盲目重发凭证。低风险自动批准属于后续明确策略，绝非模型自行授权。

## 9. 成功指标与质量门槛

- 业务闭环完成率：有授权测试账套时，上传→生成→审批→写回→回查全程真实成功；无授权时可完成到导出且准确说明阻塞。
- 每份输入原件都有处理状态；不能静默丢票、漏发票行或合并不同业务。
- 借贷不平、重复票、金额冲突、未验收、冲红/作废、跨期、缺科目都必须按规则拦截。
- 自动建议可追溯到具体文件和字段，人工能编辑并记录修改原因。
- 评测区分「单据识别准确率」「业务关联准确率」「凭证分录正确率」「ERP 写入成功/回读一致率」「异常拦截率」，不得只汇总为一个“AI 准确率”。
- 无真实第三方授权时，禁止演示界面误写“已同步/已入账”；所有外部凭据安全保管。
- 至少完成正常采购、票款不符、少入库、重复上传、多张发票、API 超时和回写幂等的自动回归测试。

## 10. 尚待业务负责人确认

首批客户类型和会计准则、是否一般纳税人/允许进项税抵扣、柠檬云实际账号版本及开放写入权限、首个试点是否开启真实写回、外部模型处理敏感票据的授权与脱敏要求、企业是否需要多级审批。这些不应被代码硬编码为通用事实。
